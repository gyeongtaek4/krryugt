## 현재 비용·운행자료 보관 방식

- 차량·계약은 Supabase에 연결되어 있다. 임시 운행·비용 및 월별 확정자료는 브라우저 메모리 중심이다.
- 확정자료는 JSON 보관파일을 내려받아 보관하고 재접속 시 복원한다.
- 비용·운행의 서버 영구 저장은 미연결이다. JSON과 원본을 별도 보관하며 브라우저 메모리를 유일한 업무 저장소로 사용하지 않는다. 차량·계약에는 로그인·RLS가 적용된다.

## 향후 구조 제안

| 데이터 | 역할 |
|---|---|
| 차량 | 내부 고유 ID, 번호, 차종, 지역·주차장 |
| 조직·담당자 | 본부·부·팀과 담당자 |

| 계약 | 차량 ID, 기간, 월 렌탈료, 업체 |
| 업로드 이력 | 원본 위치, 유형, 귀속월, 업로드일, 처리결과 |
| 운행 기록 | 차량 ID, 운행일, 누적 키로수 또는 실제 거리 |
| 마감 버전·상세 | 유형·월·버전·상태, 차량별 비용/운행과 당시 조직 |
| 정정 이력 | 이전·새 버전 연결, 사유, 처리자·처리일 |

차량 → 배정/계약/운행은 각각 여러 기록을 가질 수 있다. 마감 버전 → 상세도 여러 행을 가진다.
차량번호 변경을 고려해 내부 ID를 쓰는 방안, 중복 기준과 월중 조직 이동 처리는 실제 샘플 확인 후 확정한다.
Supabase 연결 시 원본은 비공개 Storage, 구조화 자료는 DB, 접근 제어는 로그인과 DB 권한으로 검토한다.
비밀키와 업무자료를 코드·MD에 저장하지 않는다.

## SQL 1단계 준비

`supabase/001_initial_schema.sql`은 사용자가 실행 결과를 확인했다. 표 생성과 화면의 서버 저장 연결은 별개의 단계이며 비용·운행 연결은 아직 후속 작업이다.
실행 대상은 profiles, vehicles, contracts, driving_records이며 비용·운행 마감 버전과 원본 파일 Storage는 다음 단계에서 만든다.
RLS는 활성화하지만 정책은 아직 만들지 않는다. 따라서 SQL 실행 직후 브라우저 홈페이지에서 자료를 읽거나 쓰는 것은 의도적으로 불가능하다. 로그인·권한 정책과 홈페이지 연결을 같은 단계에서 추가한다.

`supabase/002_auth_rls.sql`은 Auth 사용자와 profiles 연결, admin/editor/viewer 역할, 현재 차량·계약·운행 표의 RLS 정책을 만든다. 실행 후 관리자 이메일을 SQL의 안내 문장에 직접 입력해 role을 admin으로 승격한다. 비밀번호는 SQL이나 저장소에 넣지 않는다.
